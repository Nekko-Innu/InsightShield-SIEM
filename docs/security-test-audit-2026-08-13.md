## 1. Methodology

This is a full re-execution, not a diff review. A disposable instance of the codebase was booted from the post-fix working tree with a throwaway SQLite database and generated secrets (ENCRYPTION_KEY, FLASK_SECRET_KEY, WAZUH_WEBHOOK_TOKEN), seeded with five representative alerts (one per severity, covering all three lifecycle states) and six purpose-built accounts, then driven with genuine HTTP requests (Python's requests library) against the live Flask application. Every row below records the actual request(s) sent, the actual HTTP status/response observed, and where relevant a direct database or application-log inspection used as corroborating evidence. All 27 cases were run in a single session against a single instance, so the audit_log evidence in ST-021 and ST-027 is the log of this run.

Environment constraints are unchanged from the previous run: this sandbox has no real Wazuh manager, no outbound access to Telegram/Gmail/Groq/Gemini/OpenRouter, and no nginx/TLS/ufw in front of the app. Test cases whose subject is those integrations (ST-005's notification delivery, ST-023's Secure cookie flag under real HTTPS) were executed as far as the application logic allows and are annotated accordingly. **All 27 cases were executed live in this run** — including ST-009, which the previous run could not execute.

ST-023 is executed against a second instance of the same build, booted over real TLS (`ssl_context='adhoc'`, self-signed) with `INSIGHTSHIELD_ALLOW_HTTP_COOKIES` deliberately unset, so `config.COOKIES_REQUIRE_HTTPS` takes its production default. It cannot share the main instance: a Secure cookie is never returned over plain HTTP, so every other authenticated case would fail on a missing session. Only the certificate is synthetic — the transport, the app configuration and the cookie are the real ones.

ST-009 is executed by booting this run's instance with `INSIGHTSHIELD_SESSION_LIFETIME_MIN=1`, a new environment override added for exactly this purpose, and then idling a real 70 seconds. The default remains 30 minutes; the override only exists so the control can be exercised without a 30-minute wall-clock wait in a test run. Everything the case actually proves — that expiry is enforced server-side on the next request, and that dashboard polling does not extend the window — is independent of the number.

**Final verification round.** After the ST-001..ST-027 re-run, the working tree was put through three independent passes rather than declared finished: a diff review of every changed file, an automated code review at high effort, and a full route-by-route gate matrix built by AST extraction over all nine blueprints (41 registered routes, each checked for its `@login_required`/`@role_required` stack, CSRF exemption, and password-gate exemption). That round found three defects the 27 cases had not covered — two of them introduced or left standing by this round's own fixes — and they are recorded here as ST-028, ST-029 and ST-030. Every claim from those passes was re-verified by hand against the running application before being accepted; one claimed finding was rejected on inspection (see the gate-matrix note under §5).

As before, each test case runs from its own synthetic source IP presented via X-Forwarded-For, so that one case's deliberate login failures cannot throttle a later, unrelated case. This is valid in this setup specifically because the app trusts exactly one proxy hop (ProxyFix, intended for nginx) and the suite talks to Flask directly with nothing in front of it. ST-006 uses the same mechanism as its actual test technique rather than as test hygiene.

One methodology correction carried into this run. The previous run's ST-005 Part B attributed all 20 aged failures to a single username, which the per-username throttle (10 failures / 60 min) blocks before the per-IP escalation counter is ever read. This run spreads the 20 aged failures across 20 distinct usernames from one IP — the password-spray shape of the attack — which is the realistic path to the 20-in-60-min per-IP threshold. See the ST-005 row for what this means for the design finding.

**Changes under test since the original audit run:**

1. `web/blueprints/auth.py` — `logout()` now calls `session.clear()` **before** `logout_user()`. This is the ST-008 fix.
2. `db.py` — `verify_password()` now runs `check_password_hash()` against a module-level dummy hash when the username does not exist, so both paths pay the same scrypt cost. This is the ST-026 timing fix.
3. `web/blueprints/auth.py` + `app.py` — remember-me removed. `login_user()` is called without `remember=True` and the `REMEMBER_COOKIE_*` settings are gone, so no persistent authentication cookie is issued at all. This is half of the ST-009 fix: the 7-day remember cookie outlived the 30-minute session and re-authenticated the user the moment it expired, which made the idle timeout unenforceable.
4. `app.py` — new `_IdleTimeoutSessionInterface` stops machine-poll paths (reusing `hooks.AUDIT_SKIP_PREFIXES`) from refreshing the session cookie. This is the other half of the ST-009 fix: `/api/alerts/latest` (manager tab, 15 s) and `/api/events/stream` (IT tab) are both `@login_required`, and with Flask's default `SESSION_REFRESH_EACH_REQUEST` each poll renewed the session, so a browser left open on a dashboard never timed out.
5. `config.py` — `PERMANENT_SESSION_LIFETIME_MIN` now reads an optional `INSIGHTSHIELD_SESSION_LIFETIME_MIN` override; the default is still 30.
6. `templates/alert_detail.html` — the acknowledge and resolve confirmation modals are now inside `{% if current_user.is_it_admin %}`, like the buttons that open them. See the ST-025 row.
7. `web/auth_user.py` — comment corrections only, no behaviour change (see the Additional Observation below).
8. `tests/test_logout_session.py` and `tests/test_session_timeout.py` — regression tests for ST-008 and ST-009, so neither defect can return silently.

**Added by the final verification round (ST-028 to ST-030):**

9. `app.py` — `_retire_legacy_remember_cookie` before_request. Dropping `remember=True` stops new cookies but retires none of the ones already in browsers; Flask-Login reads `remember_token` regardless of how the app logs people in. See ST-028.
10. `templates/report.html` — the raw-payload appendix and the per-alert forensic detail block are now IT_ADMIN-only. See ST-029.
11. `web/blueprints/stream.py` — SSE streams end after one session lifetime instead of running an unbounded `while True`. See ST-030.
12. `app.py` — the machine-poll list is now its own `_MACHINE_POLL_PREFIXES` constant instead of borrowing `hooks.AUDIT_SKIP_PREFIXES`, which had wrongly included `/api/severity-breakdown` (a click handler, not just a poll). Covered by a third client in the ST-009 test.

## 2. Summary

30 test cases executed live (27 from the capstone document, 3 added by the final verification round). **30 PASS** · **0 FAIL** · **0 FINDING** · **0 not executed**

**Results of remediation:**

* ST-008 (Session Management) — **FAIL resolved, now PASS.** With remember-me removed, no persistent authentication cookie is issued at all, so there is nothing left to survive a logout. The `/logout` response expires the session cookie and the follow-up request to /dashboard/it is redirected to /login. Covered by a regression test that also asserts no valued remember_token is ever issued.

* ST-009 (Session Timeout) — **NOT EXECUTED resolved, now PASS, and it was a real defect rather than a documentation gap.** Two things had to change before an idle session could ever end: the 7-day remember cookie (which re-authenticated the moment the session expired) and the fact that authenticated dashboard polling refreshed the session cookie on every tick (which meant an open tab never went idle). Both are fixed, and both client shapes — a silent client and one polling `/api/alerts/latest` every 15 s — are now redirected to /login after the idle window.

* ST-026 (User Enumeration) — **FINDING resolved, now PASS on both message and timing.** The measured mean response-time delta between a valid username with a wrong password and a nonexistent username fell from 106.2 ms to 4.6 ms (145.1 ms vs 140.5 ms, n=5 each), i.e. inside run-to-run noise and no longer a usable oracle.

* ST-025 (IDOR, Alert Detail) — **FINDING closed as by-design, now PASS.** Manager read access to alert detail is intended behaviour per SYSTEM_DESIGN.md:40, with the IT-only content suppressed in the template. Verifying that claim did surface one real leak — the acknowledge/resolve modals rendered for Managers too — which is fixed. See the ST-025 row.

* ST-023 (Security Cookie Configuration) — **PASS (partial) resolved, now full PASS.** Re-executed against the same build served over TLS with the dev cookie flag unset: the session cookie carries Secure, HttpOnly and SameSite=Lax, and an authenticated page loads over that connection, so the configuration is functional and not merely emitted. No code change was needed — the previous partial was a test-environment limit, not a defect.

* ST-005 (Brute Force Detection) — **PASS, with the design finding restated more precisely.** The escalation alert fires for real, but this run confirms which attack shape reaches it: a single IP spraying many usernames does; a single IP hammering one account is capped first by the per-username throttle. This is the one advisory item still open, and it is a tuning decision, not a defect.

**Found by the final verification round, all three now fixed and re-tested:**

* ST-028 — removing remember-me did not disarm the remember cookies already in browsers. Flask-Login reads `remember_token` no matter how the app logs people in, so a cookie minted by the previous build kept authenticating, and kept minting fresh sessions, for its full seven days after deploy. Confirmed by crafting one and reaching /dashboard/it with HTTP 200 against the otherwise-fixed build. This is the ST-008/ST-009 bypass surviving the fix that was supposed to end it.
* ST-029 — `/report` and `/report.pdf` are open to both roles by design, and `report.html` carried no role check at all: a Branch Manager who clicked Generate received Appendix A, the original raw Wazuh decoder payload for every alert in the range, plus the per-alert forensic detail block. The PDF was worse, since the renderer force-opens every collapsed section before printing. This is the same data class ST-025 was closed on the understanding that Managers never see.
* ST-030 — an SSE stream authenticated once at connect and then ran an unbounded loop, so an open IT dashboard kept receiving live alert rows after its session had expired. Making polling stop refreshing the session (the ST-009 fix) is what turned this from theoretical into reachable.

**How the timeout behaves, since it is easy to misread:** expiry is enforced on the next request, not pushed to the browser. A tab left open on a dashboard does not visibly log itself out at the 30-minute mark; the session is dead server-side, and the next navigation — or the next poll, which will now come back as a redirect to /login — is what surfaces it. Nothing keeps a session alive except real user requests.

**Additional observation (no test case, no behaviour change):** `login_manager.session_protection = "strong"` in `web/auth_user.py` does not do what its comment claimed. Flask-Login 0.6.3's `_session_protection_failed()` evaluates `if mode == "basic" or sess.permanent:` before it reaches the strong branch, and login sets `session.permanent = True` so PERMANENT_SESSION_LIFETIME applies — so a permanent session takes the basic branch (mark the session non-fresh, keep it alive) and never reaches the strong branch that would delete it on a client-identifier change. Session revocation on this application actually rests on the password-derived token embedded in `User.get_id()`, which is independently verified by ST-022 (the old password stops working immediately after a change). The comment has been corrected; the configuration line was left as-is.

## 5. Outstanding Items

No test case is failing and none is unexecuted. Five advisory items remain, none of which blocks sign-off:

1. **ST-005** — the throttle-trip case still produces no alert of any severity. Recommendation stands: emit a low-severity alert when the login throttle trips, so a persistent single-account attacker is visible to IT and not merely rate-limited.
2. **ST-023, deployment layer** — the application's cookie attributes are now proven over TLS, so nothing is outstanding in the app. What remains is nginx's side of the same control on the VM: TLS termination with a real certificate, HSTS, and port 80 redirecting rather than serving. Worth one check before release sign-off, and note that `INSIGHTSHIELD_ALLOW_HTTP_COOKIES` must be absent from the production `.env` — setting it there would silently drop the Secure flag.
3. **ST-009, operational note** — with remember-me gone, staff are logged out after 30 minutes of genuine inactivity and must log in again; there is no "stay signed in". That is the intended trade for an enforceable timeout, but it is a visible behaviour change for anyone used to the old build, and worth saying out loud before deployment.

4. **`POST /api/client-error`, low severity** — it is the only endpoint in `api.py` with `@login_required` and no role gate (`api.py:41-42`), and it writes caller-supplied `message`, `url` and `stack` into `error_log`, a table only IT_ADMIN can read at `/admin/settings?tab=errors`. A Manager can therefore pollute an IT-only view. Bounded in practice: 10/min per user, truncated to 2000/8000 characters, and `templates/errors.html` renders the fields through plain `{{ }}` with no `|safe`, so it is log noise rather than stored XSS. Left as-is because the endpoint exists to catch browser errors from any authenticated role; if that reasoning is rejected, the fix is a `@role_required` or a per-role quota.

5. **Read-path separation is enforced in templates, not routes** — `alert_detail()` and `/report` both hand the full alert record to Jinja and let `{% if current_user.is_it_admin %}` decide what a Manager sees. That is not currently exploitable on either page (verified section by section in ST-025 and ST-029), but ST-029 is exactly what that pattern fails like: one template written without the guard, and the data is out. The durable fix is to strip IT-only fields server-side before rendering for a non-IT viewer, so a future template cannot leak them. Worth doing if these views are extended.

**Gate matrix, recorded for completeness.** All 41 registered routes were enumerated with their decorator stacks. Every mutating route carries `@login_required`, and every one whose siblings are IT-only carries `@role_required("IT_ADMIN")`. Exactly five endpoints resolve without authentication, all deliberately: `auth.login`, `api.health`, `api.api_status` (the login page's 30-second status chip, rate-limited to 30/min per IP and stripped of the per-agent list), `webhook.wazuh_webhook` (gated instead by the IP allowlist and `X-Webhook-Token`), and Flask's `static`. No route is registered twice, and no `@role_required` sits above its `@bp.route` or without a `@login_required`. One reported finding was rejected on inspection: `alerts.acknowledge` was flagged as an ungated second entry point, but it carries both decorators itself and has no `@bp.route` at all — it is reachable only by direct call from the gated alias.
